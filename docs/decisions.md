| D22 | 2026-11-14 | **The data model and database functions are the core product.** (1) As much business logic as possible lives in PostgreSQL: validation, rules, warnings, availability, suggestions and audit, in the `api` schema's views and functions, kept as migration files in `db/`. (2) The back end (FastAPI) essentially calls those database functions and reads those views. It adds only what SQL can't do well, such as file parsing, solving and notifications, and that code also goes through the same views and functions. (3) The API's OpenAPI document is the contract between UI and back end. The UI's typed client is generated from it, so another back end serving the same spec (e.g. PostgREST or Oracle ORDS) could replace FastAPI, and migrating would be a minimal burden. (4) The UI (React, served by Caddy) is a presentation layer only. It displays data, collects input and shows the warnings the API returns, and makes no decisions about what is allowed. | The schema and functions hold the value and are tested in one place; the API and UI around them are replaceable as the production platform becomes clear. Consolidates D2–D4, D16 and D21. |
| D24 | 2026-11-14 | **Multi-tenant data model.** A `tenants` table (starting with LIVE and DEMO, extensible to e.g. one per team). Every other table has `tenant_id`; links between tables include it, so a row can never reference another tenant's row. Row-level security shows and accepts only the current tenant's rows; the API selects the tenant per request with `api.use_tenant(code)`. Reference data (attribute types, rules) is per tenant. | Lets any instance offer a demo alongside live data, and leaves room for separate teams later, with isolation enforced by the database rather than by each query. |
| D25 | 2026-11-14 | **Demo data is a product feature, confined to demo tenants.** `core.load_sample_data` (migration 0004) builds the sample estate, courses and bookings with dates relative to today; `api.reset_demo_data()` wipes and reloads the current tenant and refuses unless it is a demo tenant. Supersedes the step 1.4 approach of a seed file kept outside migrations. | One reset path for developers and the UI's "Reset demo data"; live tenants can never receive sample data. |
| D26 | 2026-11-14 | **Allocation management needs nothing beyond the data model and its SQL functions.** The UI performs no direct database operations, only API calls, and the API is the `api` schema's views and functions. More complex decision engines, such as an optimiser, are separate apps: their inputs come from GET requests on `api` views, and their outputs are applied through `api` functions, so they never bypass the rules. | The core product (D22) is complete for managing allocations on its own, and portable outside this example; anything beyond management plugs in through the same API. | D27 | 2026-11-14 | **The API is the official PostgREST image, configured only.** It serves the `api` schema as HTTP (`GET /<view>`, `POST /rpc/<function>`); a SQL pre-request hook applies the `X-Tenant` and `X-User` headers. Supersedes D16; the FastAPI generic layer remains in git history as the reference for a non-PostgreSQL back end. | Shows beyond doubt that the only way into the data is through SQL-defined views and functions: the core product is the data model and functions (D22). ## Implementation decisions

How the solution is built and run. These can change without affecting the design decisions above.

| # | Date | Decision | Why |
|---|---|---|---|
| I1 | 2026-11-14 | Migrations run in the official dbmate image, unchanged; a separate one-shot `db-roles` service (official `postgres:16` image) sets role passwords from `.env` after each migration run. | No custom images for migration tooling; passwords never live in migrations or git. |
| I2 | 2026-11-14 | The deployed `db` service uses the official `postgres:16` image, unchanged. Database tests run in a test-only service, `db-test` (Compose profile `test`), whose image (`db/test/Dockerfile`: `postgres:16` + pgTAP + `pg_prove` + dbmate) starts a throwaway database, applies all migrations from scratch, runs the tests and exits. | No custom database image in deployment; pgTAP never enters the real database; every test run also proves the migrations apply cleanly to an empty database. |
| I3 | 2026-11-14 | All `core` and `api` objects are owned by `app_owner`, a role that is not a superuser and cannot log in. Each migration creates its objects after `set local role app_owner` and ends with `reset role`. Row-level security is FORCEd. | Superusers bypass row-level security; owning everything with a non-superuser means tenant isolation also applies inside api views and functions. |
| I4 | 2026-11-14 | The API takes the tenant from the `X-Tenant` request header (falling back to `DEFAULT_TENANT`, normally empty) and calls `api.use_tenant` at the start of each request's transaction. Until logins exist, an optional `X-User` header names who is acting (default `anonymous`) and is passed to the database as `app.user` for the audit log. The API reads the `api` schema's views and functions from the PostgreSQL catalogue at startup (and again when a request names one it hasn't seen), so new database objects need no API code. | Keeps the API generic and the tenant choice explicit per request; auth can later replace the headers without changing the database. |
| I5 | 2026-11-14 | PostgREST connects as `api_user` and switches to `api_access` for each request. `api_internal.pre_request` (a separate schema, so it is not an endpoint) sets `app.user` from `X-User` (default `anonymous`) and calls `api.use_tenant` from `X-Tenant`; no header means no tenant. `db-roles` sends `NOTIFY pgrst, 'reload schema'` after every migration run. The contract snapshot is `db/api-contract.txt`, read from the `api` schema (`scripts/api-contract.sh`). Supersedes I4. | Keeps tenant and user handling in SQL and tested by pgTAP; new database objects appear without restarting the API; contract diffs stay readable. |
| I6 | 2026-11-14 | The UI (D21) is built by a multi-stage `ui/Dockerfile` from official images only: `node:22` runs the Vite build, then `caddy:2-alpine` serves `dist/` (SPA fallback) and proxies `/api/*` to PostgREST. The typed client is generated from PostgREST's OpenAPI (converted from Swagger 2.0). | A thin image with no code of its own; the build output is plain static files, so a static host remains an option. Caddy over Python's `http.server` (not for production, no fallback or proxy) and over a distroless build (harder to debug for little gain at PoC stage). |
